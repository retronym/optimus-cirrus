## 1. The model

**What a tracker is.** `DependencyTracker` (DependencyTracker.scala:47) is metadata attached to one mutable scenario level: it owns a mutable tweak set, the `ScenarioStack` objects that evaluations use, two `TweakableTracker`s that record which nodes read which tweakables, user-tracked nodes (UTracks), and a queue that serialises updates against evaluations. It is not a `Scenario` (comment at :35).

**Tree.** `DependencyTrackerRoot` (DependencyTrackerRoot.scala:46) is a `DependencyTracker` with `root eq this`, plus `CallbackSupport`, `GarbageCollectionSupport`, `TraversalIdSource`. Children are created by `newChildScenario` (DependencyTrackerChildren.scala:72–98) or `root.getOrCreateScenario(ref)` (DependencyTrackerRoot.scala:223) and identified by a `ScenarioReference`. A child is either *consistent* (shares the parent's queue, `shareParentQueue = !introduceConcurrentSubtree`, ScenarioReference.scala:113; DependencyTracker.scala:80–82) or a *concurrent subtree root* with its own `DependencyTrackerQueue`. `parent` is derived from `parentScenarioStack.tweakableListener` (DependencyTracker.scala:66–74). Names are unique across the whole root (`namedStructureBuilder`, DependencyTrackerRoot.scala:183, guarded by `withNameLock` :301). `rootOfConsistentSubtree` decides which queue an update runs on.

**State owned per tracker.**
- `tweakContainer` (DependencyTracker.scala:128): `MutableTweakContainer` owning a `MutableSSCacheID` (TweakContainer.scala:104), i.e. a `JHashMap` of tweaks plus `TPDMask`, mutated in place; or `ImmutableTweakContainer` for `rejectTweaks`. Three permanent tweaks (`ScenarioReference.current`, `currentOverlay`, `DependencyTrackerRootWeakReference.current`, TweakContainer.scala:68–73).
- `scenarioStack` (DependencyTracker.scala:144) and `nc_scenarioStack` (:150): two `final val` stacks created once by `createChildForTrackingScenario` (ScenarioStack.scala:545), both carrying the *same* mutable `_cacheID`, `tweakableListener = tweakableTracker`, empty `Scenario`. Tweaks change by mutating the shared cache id, not by building new stacks. The stack's `_parent` (a plain var, ScenarioStack.scala:150, `setParent` :1148) is the *underlay* stack, replaced by `doSetUnderlay` (UnderlayScenarioSupport.scala:31–38). Evaluations use per-cancel-scope copies cached in `scenarioStackWithCancelScopeCache` / `nc_…` (DependencyTracker.scala:191–215; copies share `_cacheID`, freeze `_parent`).
- `tweakableTracker` (:111) for the mutable level and `underlayTweakableTracker` (:87) for the underlay stacks; child-propagation lambdas at :95–103 and :119–121; both use `root` as `idSource` and `queueOwner.doClearTracking` for invalidate-all.
- `nodeInputs: MutableNodeInputMap` (:76) for plugin tags.
- `userNodeTrackers` CHM keyed by `TrackingScope` (:152).
- `currentEvaluator` volatile (:171), set by `DependencyTrackerBatchUpdaterRoot` construction (DependencyTrackerBatchUpdater.scala:340).
- Snapshot caches `_asBasicScenarioStack`, `_snapshotScenarioStack` (SnapshotSupport.scala:38–39).
- `childrenImpl` plain var + `childrenDependency` TTrack under `dependencyLock` (DependencyTrackerChildren.scala:28–31).
- `_disposed` volatile (DisposalSupport.scala:26).
- Root only: callback lists (CallbackSupport.scala:20–22), `traversalId`/`resetId` plain vars (DependencyTrackerRoot.scala:100–102), `namedStructure*` (:166–183), `reportChange` public var (:157), cleanup scheduler (GarbageCollectionSupport.scala:42).

**Lifecycle.**
- *Create*: `DependencyTrackerRoot(parentSS)` (DependencyTrackerRoot.scala:626) requires a non-tracking parent stack (:149). Construction installs an empty underlay (DependencyTracker.scala:185), registers a shutdown hook on the parent stack's `RuntimeEnvironment` (DependencyTrackerRoot.scala:70–84) and records the root in a global `WeakHashMap` (:305, :375). Children: `newChildScenario` constructs the tracker, `addChild` + `root.addedChild` (both fire TTrack invalidations, see A4), then sync `child.addTweaks` (DependencyTrackerChildren.scala:93–97). Construction itself is not queued.
- *Update*: `executeBatchUpdate(Async)` → `TSA_BatchUpdate` (DependencyTracker.scala:391) → batch updater; public `addTweaks`, `setUnderlay`, `dispose` are sugar over it (DependencyTrackerSyncApi.scala:37–110, DependencyTrackerAsyncApi.scala:34–123).
- *Evaluate*: `evaluateNodeKey(s)`, `executeEvaluate`, async variants, low-priority variant, `reevaluateTrackedNodesAsync` (root), `snapshotScenarioAsync`; plus evaluations *inside* a batch (`evaluateNodeKeysImmediate`, `evaluateImmediate`, `evaluateNodeKeysAsync`, `evaluateAsync`).
- *Dispose*: always on the **root** queue (`dispose`, DependencyTrackerSyncApi.scala:96; `disposeAsync`, DependencyTrackerAsyncApi.scala:113) → `doDispose` (DisposalSupport.scala:30) → depth-first `disposeThisAndChildren` (:56), `ttracks = null`, UTracks disposed, snapshot tweaks removed, `notifyScenarioDisposal` user callbacks, `Caches.lazyClearDisposedTrackers`.

**Callers (entry points and threads).** In this repo almost all callers are outside `core` (UI/reactive code is not in the OSS tree; `getCurrentEvaluator`, `scenarioState` have no callers here).
- UI / user threads: sync API (`execute` blocks on a `CountDownLatch`, DependencyTrackerAction.scala:207) and async API (registration on the caller thread, the first action may *run* on the caller thread via `scheduleAction`).
- Graph threads: every async action runs as a node (`DependencyTrackerActionTask`, DependencyTrackerAction.scala:46); completion callbacks, `afterActionCompleted` and the dispatch of the next actions run on whichever graph thread completed the previous action. Reactive handlers call the batch updater's `DependencyMultiTrackerEvaluator` from node-completion callbacks (DependencyTrackerBatchUpdater.scala:125–172).
- Timer thread: `CleanupScheduler` via `timedScheduler` → `cleanupAsync` (GarbageCollectionSupport.scala:42–46); GC monitors → `DependencyTrackerRoot.runCleanupNow` (DependencyTrackerRoot.scala:402).
- JVM shutdown: `root.dispose()` (sync) from the environment's shutdown action.

## 2. The queue

**Single-writer model.** One `DependencyTrackerQueue` per concurrent subtree root (DependencyTrackerQueue.scala:42). State: `workQueue`, `lowPriorityQueue` (plain `ArrayDeque`, guarded by `queueLock`, :184–186), and `stateManager` (:66) with volatile `stateUpdating`, `parentIsWaiting`, `inFlightWorkSet` (an immutable `Set` replaced under `queueLock`). Rules enforced in `recordStart` (:126–145): an update may start only if nothing is in flight; an evaluation may not start while an update is in flight. Any number of evaluations run concurrently. Per queue, therefore: updates are exclusive, evaluations are shared, i.e. a reader/writer lock implemented as a work queue.

**Ordering.** `registerOrEnqueueAction` (:206–263): an update is immediate only if nothing is in flight and it is at the head (`workQueue.isEmpty || highPriority`); an evaluation is immediate if no update is in flight and it is at the head. Otherwise it is appended (or `addFirst` for `highPriority`, :248). `afterActionCompleted` (:288–369) is the only dispatcher: when nothing is in flight, `findWork` pops either one update or a maximal run of consecutive evaluations (:314–333), from `workQueue` first, then `lowPriorityQueue`, then releases the parent (:339–343). FIFO between updates and evaluations is preserved; `highPriority` jumps ahead of queued updates (used for cleanup, :615, and exposed on `executeBatchUpdateAsync`).

**Nesting of queues.** A child queue is itself an action on the parent queue (`DependencyTrackerQueue extends DependencyTrackerActionEvaluateBase`, :43). Before a child runs anything it registers with the parent (`registerOrEnqueueActionParent`, :194, called with the child's `queueLock` held → parent's `queueLock`: lock order child → parent). The parent sees the whole child queue as one in-flight *evaluation*; the child gives it back only when both its queues are empty (:339–343). Consequence: a parent update waits for every descendant queue to drain; siblings run concurrently with each other, including concurrent *updates* in sibling subtrees.

**Threads.** Registration on the caller's thread. Immediate async actions run `scheduleAction` on the caller's thread (:537); queued ones on the thread that completed the previous action (:352–365). Sync `execute` runs the action body on the caller's thread (`executeSync` → `EvaluationContext.evaluateSync`, DependencyTrackerAction.scala:389–397, :463–472). Async bodies are nodes on `Scheduler.defaultMT` (or the scheduler passed into `TSA_BatchUpdate`, which defaults to `Scheduler.currentOrDefault`, DependencyTrackerAsyncApi.scala:91, contradicting the comment at DependencyTrackerAction.scala:111–115).

**Cancellation scopes = the barrier.** Every evaluation phase gets a fresh scope, a child of the parent queue's current scope (`newChildOfParentScope`, :403; `setNewCancellationScopeBeforeEvaluating`, :426). When the last evaluation of a phase stops, and after every update, `cancelOrphanedNodesAndResetCancellationScope` (:439–445) cancels the scope, waits for running cancelled nodes on *all* schedulers (`waitForCancelledNodesToStop`, OGScheduler.java:1627) and nulls the scope. Before an update runs, `evaluationBarrier` (:412–421) does the same and installs a new scope for the update. The batch updater calls `evaluationBarrier` again before *every* mutating op (DependencyTrackerBatchUpdater.scala:213–219, :476–490). This is the mechanism that keeps TTrack mutation (evaluation) and TTrack traversal (invalidation) apart; the rationale is at :371–389.

**Batching (`DependencyTrackerBatchUpdater`).** One update action = one `DependencyTrackerBatchUpdaterRoot` (DependencyTrackerBatchUpdater.scala:333) targeting the consistent root, with `DependencyTrackerBatchUpdaterView`s for descendants (:753). Single-threaded by contract (`checkInvariants`: `initialNode eq EvaluationContext.currentNode`, :496–500, Scala `assert`). Inside a batch, async evaluations are allowed and tracked by a counter (`StateManager`, :375–461): `tryIncreaseEvaluating` refuses while `updating` or `closed`; each mutating op first spins (`Thread.yield` / `runAndWait` on pending nodes, :449–458) until the counter is zero, sets `updating`, then calls the queue barrier; `finishUpdating` clears it. `close()` (:502) does a final barrier and then fires the batched invalidation callbacks (`invalidationBatcher.complete()`).

**Re-entrancy.** None by design. Sync `execute` from inside an evaluation on the same queue runs nested if it happens to be immediate and deadlocks if an update is queued (the update waits for the outer evaluation, which waits for the nested action queued behind the update). `addTweaks` documents this (DependencyTrackerSyncApi.scala:65–66); `checkForDeadlock` only logs (DependencyTrackerAction.scala:222–236).

**Exceptions.** Sync path: `beforeAction`/`executeSync` in `try`, `afterAction` and `afterActionCompleted` in `finally` (DependencyTrackerQueue.scala:510–527). Async path: `beforeAction` failure → `afterActionCompleted` + rethrow, but no `afterAction` (token leaked) and no `raiseCallback` (:452–458); `executeAsync` failure → nothing (A1). Exceptions inside `afterActionCompleted`'s locked section leave the queue undispatched (A7).

**Cancellation mid-action.** Only low-priority actions are cancellable (`EvaluateNodeKeysLowPriorityAction`, DependencyTracker.scala:281–332): an incoming update calls `cancelAndRescheduleLowPriorityActions` under `queueLock` (DependencyTrackerQueue.scala:226–228, :269–282), which cancels the action's child scope, waits for its nodes to stop, and enqueues a retry for incomplete keys. The cancelled action stays in flight until its (cancelled) nodes complete.

**Disposal mid-action.** Disposal runs on the root queue, so all descendant queues are idle when it runs. Queued actions for a disposed tracker complete with `DependencyTrackerDisposedException` via `alreadyDisposedResult` (DependencyTrackerAction.scala:379–384, :406–412, :481–487), the callback deferred through `scheduler.evaluateAsync` to avoid stack growth. Construction-time checks (`executeBatchUpdateAsync` :99) are TOCTOU but re-checked in `asNode`.

**Completion path.** Async single-node actions: `scheduler.evaluateNodeAsync(node, …, cb, cbSS = ScenarioStack.constantNC)` (DependencyTrackerAction.scala:418–430) → `SchedulerAsyncCallback` enqueued (inline only if `threadsIdeal == 0`, Scheduler.scala:357) → `afterExecute` = `afterAction` (token release) → `raiseCallback` (user callback) → `afterActionCompleted` (DependencyTrackerQueue.scala:468–489). Many-node actions: `scheduler.evaluateNodesAsync(nodes, doneCallback)` with default `callbackInline = false` (DependencyTrackerAction.scala:494–501): the completion counter is attached to the **caller's** scenario stack (Scheduler.scala:269–273) and enqueued (:279–280); see A3. Batch-updater async evaluations pass `callbackInline = true` (DependencyTrackerBatchUpdater.scala:667–678, :723–731), the case the scheduler review noted: the callback runs inline on the thread that completed the last node, because the batch updater may be spinning on a graph thread in `waitForEvaluations` and would otherwise deadlock with no free thread. Inline callbacks also skip the cancelled-scope check in `OGSchedulerContext.run` (OGSchedulerContext.java:854–856), which is what makes the batch path immune to A3.

## 3. The update path end to end

Example: `tracker.addTweaksAsync(tweaks, cb)` on a consistent child of a concurrent subtree root R.

1. **Registration** (caller thread; `queueLock` of R's queue; if R is not the root, R's lock then parent's lock, DependencyTrackerQueue.scala:212–224). `TSA_BatchUpdate` constructed (its `token` is taken at construction, DependencyTrackerAction.scala:276). If nothing is in flight: `recordStart`, `stateUpdating = true`; then outside the lock `evaluationBarrier` (:259–261), normally a no-op cancel because the previous phase already nulled the scope, and installs scope S_u. Otherwise appended, and dispatched later by `afterActionCompleted` on a graph thread, which also runs the barrier (:353–355).
2. **Run** (graph thread, no tracker lock). `DependencyTrackerActionTask(update)` attached to `ScenarioStack.constantNC` (DependencyTrackerAction.scala:143–147, :246, :546–550). `doUpdate` → `root.getOrCreateScenario(rootOfConsistentSubtree)` (`nameLock`), `new DependencyTrackerBatchUpdaterRoot` (sets `currentEvaluator`), user lambda (DependencyTracker.scala:399–406).
3. **Per op** `addTweaksImmediate` → `addTweakMapImmediate` → `runUpdate` (DependencyTrackerBatchUpdater.scala:221–229, :525–541): `beforeAccessTarget(forUpdate = true)` → `waitForEvaluations` (spin; StateManager lock) → `queue.evaluationBarrier` (cancel S_u, `waitForCancelledNodesToStop` on every scheduler, which takes each scheduler's `_lock` while snapshotting stacks, OGScheduler.java:1661; new scope S_u').
4. **Tweak lambdas** (`UpdateMultipleScenarios`, UpdateMultipleScenarios.scala:24–66): lambdas evaluated in `nc_scenarioStack.withCancellationScope(S_u')`, waited, then another `evaluationBarrier` (S_u'') before any mutation.
5. **Mutation, per tracker, sequentially** (`MutableTweakContainer.doAddTweaks`, TweakContainer.scala:107–130): build `Scenario(tweaks)`; if it has unresolved/marker tweaks, **expand by evaluating** `ExpandTweaksNode` in `scenarioStackWithCancelScope(S_u'')` (TweakExpander.scala:40–46; a cacheable `PropertyNode` looked up in the tracker stack); `cacheId.changesFrom` (CacheIDs.scala:414); `cacheId.putAll` — **unsynchronised `JHashMap` writes and `TPDMask` merge**, relying on the comment at CacheIDs.scala:408–412 that the queue keeps evaluations out; `invalidateSnapshot` (volatile nulls up/down the tree); `OverInvalidationDetection.set(cause)`; `tweakableTracker.invalidateByTweaks` (TweakableTracker.scala:160).
6. **Finding nodes** (same thread; no tracker lock; `ttracks` is a CHM). Instance tweaks: `invalidateByKey` gets/removes the `TTrackRoot` for the key and traverses callers with `Invalidators.invalidate` (TweakableTracker.scala:218–232), recursing into children whose stack does not already instance-tweak the key (DependencyTracker.scala:95–103, :119–121). Property tweaks: scan all roots (TweakableTracker.scala:262–284). Non-tracked properties: clear caches and all tracking in the consistent subtree (:174–176, :286ff). The traversal id comes from `root.withFreshTraversalId` (DependencyTrackerRoot.scala:116–134; plain vars, A5).
7. **`invalidateCache`** on each reached node (`Invalidators.java:33`): `NodeTask.invalidateCache` = one `updateState(set INVALID_CACHE|NOT_RUNNABLE, clear DONE_FLAG)` (NodeTask.java:1140–1145); tracked nodes override to report to the observer, here the batch's `InvalidationCallbackBatcher` (CallbackSupport.scala:165–179). The tracker assumes every reached node is quiescent (not running) because of the barrier, which is what keeps it out of R6/R8 territory; A4 is the exception.
8. **Close** (`DependencyTrackerBatchUpdaterRoot.close`, DependencyTrackerBatchUpdater.scala:502–506): final barrier, then user `nodesInvalidated` callbacks on the update's graph thread, still inside the update action. Typical callbacks call `reevaluateTrackedNodesAsync` (DependencyTrackerRoot.scala:323), which enqueues `EvaluateNodeKeysAction`s behind the running update.
9. **Completion**: update node completes → `SchedulerAsyncCallback` (constantNC) → `afterAction`, `raiseCallback` (user `cb`), `afterActionCompleted` → `recordStop`, `cancelOrphanedNodesAndResetCancellationScope` (under `queueLock`), `findWork` dispatches the re-evaluations, each running `nodeOf` (DependencyTracker.scala:217–232): UTrack lookup, `ss.getNode(key.prepareForExecutionIn(ss))` on the cancel-scope copy of the tracker stack, `registerRunningNode`.

**Visibility to concurrent evaluations.** Within one queue, none: no evaluation of that queue is running during steps 3–8, and none of a descendant queue (parent update waits for children to drain; their scopes are children of the cancelled one). Happens-before from the update's writes to the next evaluation comes from `queueLock` (dispatch) and scheduler enqueue. From evaluations to the update, the HB edge is the barrier's polling of `getCurrentNodeTask` in `waitForCancelledNodeToStop` (OGScheduler.java:1679) plus `queueLock`; not checked whether those fields are volatile (assumption to verify in ring 1/scheduler notes).

**Torn reads.** An evaluation that started before an update cannot observe the update's tweaks *and* complete: if still running at the barrier it is waited for; if suspended, its scope is cancelled and it is completed with cancellation instead of run (OGSchedulerContext.java:854–856). Places where a mix *is* observable:
- A9: inside one multi-scenario batch, tweak expansion for scenario k evaluates against the batch with scenarios 1..k-1 applied.
- A12: any evaluation in the tracker's stack that is not in a queue-managed cancel scope (public `scenarioState`, `nc_scenarioStack`).
- A4: off-queue invalidations hit running nodes.
- A8: plugin tags.
- Siblings in different concurrent subtrees are concurrent by design; they share no mutable tweak state (each mutates only its own `MutableSSCacheID`), so no torn read between them, but they share the root's traversal counter (A5).

**Lock nesting observed.**
- child `queueLock` → parent `queueLock` (registration :212–224, release :342, invariant checks :119–121). No reverse path found.
- `queueLock` → action monitor (low-priority `cancel`, :274; DependencyTracker.scala:305) → scheduler `_lock` (inside `waitForCancelledNodesToStop`, OGScheduler.java:1661) for every scheduler.
- `queueLock` → scheduler `_lock` also from `cancelOrphanedNodesAndResetCancellationScope` (:439–445). The reverse (scheduler `_lock` → `queueLock`) would need a stall callback or out-of-work listener that touches a tracker; none is registered in `tracking/`.
- `nameLock` → (`new DependencyTracker`) → `dependencyLock` → TTrack traversal → `NodeTask.updateState` CAS → user invalidation callbacks (`unbatchedTrackedNodeInvalidationObserver`, CallbackSupport.scala:70–80). User code under two internal locks.
- `EventCause` child → parent monitors.
- `StateManager` monitor: leaf.
- `NodeTask._visitLock` and cache locks: not taken by ring 4a directly; reached via `ss.getNode` in `nodeOf` and via `invalidateCache` (CAS only).

**Calls out while holding a lock.** Under `queueLock`: `waitForCancelledNodesToStop` (unbounded wait on other threads' nodes), low-priority `cancel()` including lazy `nodes` → `nodeOf` → `ss.getNode` (cache, tweak resolution) (A13), `parentDependencyTracker.queue.afterActionCompleted` (recursive dispatch upwards), `trackerRoot.logStalling` (diagnostics). Under `nameLock`/`dependencyLock`: tracker construction, TTrack traversal, user callbacks. User completion callbacks (`raiseCallback`) are called *without* `queueLock`, which is good, but while the action is in flight (A2).

## 6. Suspects by lens

### Races / liveness

<a id="a1"></a>**A1 (H) A synchronous throw from `executeAsync` wedges the queue.** `scheduleAction` (DependencyTrackerQueue.scala:447–491) calls `action.executeAsync { … afterActionCompleted(action) }` with no `try`. Everything before the node is handed to the scheduler runs synchronously: `asNode`/`asNodes` → `nodeOf` (DependencyTracker.scala:217–232: `userNodeTracker(..).getUTrack`, `key.prepareForExecutionIn`, `ss.getNode`, i.e. cache lookup running user `argsHash`/`argsEquals`), `OGSchedulerContext.current.getCurrentNodeTask` (DependencyTrackerAction.scala:490, NPE on a thread without EC), `EvaluationContext.current` (NPE, EvaluationContext.scala:192–197), `attachCauseInfoAndScenarioStack`. A throw there happens after `recordStart`, so the action stays in `inFlightWorkSet`, `afterAction` (token), `raiseCallback` and `afterActionCompleted` never run. Every later action on that queue is enqueued and never dispatched; if it is a child queue, the parent also waits forever for it. The exception goes to the `executeAsync` caller if immediate, or into the previous action's completion callback's `finally` (swallowed as a node exception) if dispatched. Inputs: a node key whose `argsHash`/`equals` throws, or the first async action issued from a thread with no EvaluationContext. The sync sibling `execute` (:510–527) has the `finally`; inconsistent siblings. Needs probe: a key with a throwing `argsHash` passed to `evaluateNodeKeyAsync`, then a second action, observe it never runs.

<a id="a2"></a>**A2 (H consequence, needs misuse) Callbacks run while the action is in flight.** `raiseCallback` runs before `afterActionCompleted` (:476, :486), and batch invalidation callbacks run inside the update (`close()`, DependencyTrackerBatchUpdater.scala:502–506). A callback that calls any *sync* API on the same queue (`addTweaks`, `executeBatchUpdate`, `evaluateNodeKey` when an update is queued) registers, is not immediate, blocks on the latch on a graph thread, and the action it is waiting behind cannot complete because its completion is the callback. Permanent; `checkForDeadlock` only logs (DependencyTrackerAction.scala:222–236). Same for `newChildScenario(ref, tweaks…)` called from inside an evaluation on the parent's queue (sync `child.addTweaks`, DependencyTrackerChildren.scala:97). The natural UI pattern "on evaluation result, add a tweak" hits this if written with the sync API.

<a id="a3"></a>**A3 (M) Completion counter attached to a cancellable caller stack.** `DependencyTrackerActionManyNodesBase.executeAsync` (DependencyTrackerAction.scala:480–503) → `Scheduler.evaluateNodesAsync` with `callbackInline = false`: the completion counter is attached to `EvaluationContext.scenarioStackOrNull` of the thread running `scheduleAction` (Scheduler.scala:269–273) and enqueued when the last node completes (:279–280). If that stack's cancel scope is cancelled by then, `OGSchedulerContext.run` calls `cancelInsteadOfRun` (OGSchedulerContext.java:854–856): `doneCallback` never runs, the action never completes, queue wedged. The single-node path explicitly passes `cbSS = ScenarioStack.constantNC` "otherwise we are called back in node's SS which may have been cancelled, in which case the callback would never run" (DependencyTrackerAction.scala:426–428); the many-node path does not. Interleavings: (a) a node evaluating in tracker T calls `T2.evaluateNodeKeysAsync`/`executeEvaluateAsync`/`reevaluateTrackedNodesAsync` (T2 ≠ T's queue, e.g. a sibling concurrent subtree) and the action is immediate; T's phase ends and cancels its scope before T2's nodes complete. (b) the same from inside a low-priority action on T's own queue: an incoming update cancels the low-priority child scope immediately (:226–228), while the new action is still running. The stack also propagates: a dispatch from inside a completion counter's `run` inherits that counter's stack. Needs probe; the fix is one argument (pass `ScenarioStack.constantNC` for the counter, or `callbackInline = true`).

<a id="a4"></a>**A4 (M) TTrack invalidation outside the queue.** `addChild` → `fireChildDependency` (DependencyTrackerChildren.scala:41–46, :52–55) and `DependencyTrackerRoot.addedChild` → `fireNamedStructureDependency` (DependencyTrackerRoot.scala:175–188) call `Invalidators.invalidate` on TTracks that *any* evaluating node anywhere in the root may have joined (`takeChildDependency` via `childrenWithDependency`, `takeNamedStructureDependency` via `allNamedChildren`/`childByName`). They run on whatever thread calls `newChildScenario`/`getOrCreateScenario`: a UI thread, or an update action on *one* queue, while other queues evaluate. This is exactly what the barrier exists to prevent (DependencyTrackerQueue.scala:371–376): traversal and `postVisit` (`ptracks = Ptracks0`, `nodes = Invalid`, Invalidators.java) run concurrently with `combineXinfo`/`addCaller` from evaluating nodes, and `invalidateCache` can hit a running node (the R6 and R8 shapes). The user invalidation callbacks fire unbatched, from that thread, under `nameLock` and `dependencyLock`. `getOrCreateScenario` also holds `nameLock` across tracker construction. `DependencyTrackerBatchUpdaterRoot.updaterFor(ref)` creates the tracker before asserting it is in scope (DependencyTrackerBatchUpdater.scala:363–371), so an out-of-scope ref creates a tracker (and fires) before failing. Removal paths (`removeDisposedChildren`, `removedDisposedNamedChildren`) run in the root-queue dispose and are safe. Needs probe plus the ttracks reader's view of what a concurrent `postVisit` does to a TTrack mid-`addCaller`.

<a id="a5"></a>**A5 (M) Root traversal counter shared by concurrent queues.** `withFreshTraversalId` reads and writes plain `traversalId` (DependencyTrackerRoot.scala:116–134); every `TweakableTracker` in the tree uses the root as `idSource` (DependencyTracker.scala:93, :117; TweakableTracker.scala:229–230). Two concurrent subtrees updating at once, or A4 racing an update, can both read N and both use N+1. `MarkingGraphTraverser.shouldVisit` skips a TTrack whose `lastUpdateTraversalID == id` (MarkingGraphTraverser.java:30–36), so if the two graphs share a TTrack, the second traversal stops at it and does not invalidate its callers: lost invalidation, stale value served until something else invalidates it. Graphs do share TTracks across trackers (byName tweaks reach into descendants, TweakableTracker.scala:330–331; A4's TTracks are joined by nodes in every tracker). `resetAllTraversalIds` (:139–147) rewrites ids on *all* trackers' TTracks, including those of sibling subtrees mid-traversal, and runs after any traversal that throws (:127–132). Needs a model or probe; ask the ttracks reader whether sibling subtrees can share a TTrack outside A4.

<a id="a6"></a>**A6 (M) Interrupted sync waiter strands its action.** `execute` (DependencyTrackerQueue.scala:493–529): `registerOrEnqueueAction(prepareWait = true)`, then `action.await()` (DependencyTrackerAction.scala:207–220). `CountDownLatch.await` throws `InterruptedException`; the action is still queued. Later `findWork` `recordStart`s it, `wakeUp()` returns true (latch exists, :206) so `scheduleAction` is skipped (:360–363); nobody runs it; it is never stopped. Queue wedged. UI frameworks interrupt threads (e.g. cancelled `SwingWorker`/executor shutdown).

<a id="a7"></a>**A7 (M) Waiting for cancelled nodes under `queueLock`.** `afterActionCompleted` holds `queueLock` while `cancelOrphanedNodesAndResetCancellationScope` cancels and waits (DependencyTrackerQueue.scala:292–306, :439–445); `registerOrEnqueueAction` holds it while low-priority `cancel()` waits (:226–228; DependencyTracker.scala:305–312). For a child queue the parent's lock is also held (:342). (a) Deadlock: an orphan still running in that scope (the second branch of an `apar` whose first branch threw, the case the barrier exists for) that calls `executeAsync`/`evaluate*Async`/`hasPendingWork`/`summary` on that queue blocks on `queueLock` and never stops; the waiter spins forever. (b) Latency: every producer, including the UI thread registering an action, blocks for as long as the slowest orphan takes to reach a cancellation point. (c) This runs on a graph thread inside a callback node, the R11 shape: if the scheduler's self-deadlock guard throws `GraphInInvalidState` (OGScheduler.java:1680–1694), it escapes the locked block after `recordStop` and before `_currentCancellationScope = null` and `findWork`: no dispatch, and the next evaluation registration throws "A previous cancellation scope is not cleaned!" (:430–431) until an update happens to arrive. Queued actions stay stranded (see the invariant table).

<a id="a10"></a>**A10 (M, perf) Busy concurrent child starves parent updates.** A child queue with work in flight self-approves new work (`okWithParents = true` when `workInProgress`, :218–219), and when its main queue empties it runs its low-priority queue before releasing the parent (:335–343). The parent's update waits for the child queue action to complete; preemption (`cancelAndRescheduleLowPriorityActions`) only scans the parent's own in-flight set (:269–279), which contains the child *queue*, not its cancellable actions. A child fed evaluations or low-priority work continuously (a ticking UI) delays root updates and cleanups without bound.

<a id="a11"></a>**A11 (M) Unsynchronised invalidation batches.** `evaluateNodeKeysAsync` with `removePendingInvalidate = true` is callable from other graph threads (`checkInvariants(allowAccessFromOtherGraphThreads = true)`, DependencyTrackerBatchUpdater.scala:654, :661) and mutates `InvalidationCallbackBatch.pending` via `removeMatching` (CallbackSupport.scala:153–157, comment claims concurrency-awareness but nothing locks), concurrently with other callers doing the same and with `copyNodes` (`allInvalidatedNodes`, :508–523). `callbackBatches` is a plain lazily-initialised var (CallbackSupport.scala:167–171). Outcome: lost removals (duplicate invalidation callback to the UI, benign) or a corrupted `mutable.HashMap` (exceptions in a callback path).

<a id="a13"></a>**A13 (L–M) Low-priority `cancel()` forces `nodes` under `queueLock` on the registering thread.** If an update registers between `findWork`'s `recordStart` of a low-priority action and that action's `asNodes`, `cancel()` (DependencyTracker.scala:305–330) evaluates the lazy `nodes` (:257–261): `nodeOf` and `ss.getNode` under `queueLock`, using `EvaluationContext.current`, which throws NPE on a thread without EC. The throw escapes `registerOrEnqueueAction` (the update is lost to the caller as an exception); `actionCancelled` is already true so no retry is scheduled, and when the action later runs, its nodes are attached to the cancelled scope and its callback reports `Success` with cancelled nodes (`adaptedNodeKeysCallback`, DependencyTrackerAsyncApi.scala:76–85). Narrow window.

**A14 (L, needs probe) ST mode and low-priority cancel.** With `threadsIdeal == 0`, completion counters run inline (Scheduler.scala:279). `cancel()` holds the action monitor while waiting for the action's cancelled nodes to stop (DependencyTracker.scala:305–312); a node completing inline on another thread runs `afterAction`, which is `synchronized` on the same action (:294) while that node is still on its stack. Waiter waits for the node to leave the stack; the node's thread waits for the monitor. The synchronisation that fixes the cancel/afterAction race (:291–294) creates this.

### Data loss and wrong results

<a id="a8"></a>**A8 (M) Plugin tags.** (a) `setPluginTag`/`clearPluginTag` in the batch updater use `logTimedCommand`, not `runUpdate` (DependencyTrackerBatchUpdater.scala:250–255), so they do not wait for the batch's async evaluations or cancel orphans; `PluginTagSupport.setPluginTag` is also public on `DependencyTracker` with no queue at all (PluginTagSupport.scala:19–41). (b) `MutableNodeInputMap.freeze` (ScenarioStack.scala:1454–1472) is check-then-store against a non-volatile `tagsThisLevelOnly`: T1 enters `freeze`, reads the old tags; T2 `addInput` updates tags and nulls `cache`; T1 stores the map built from the old tags. The stale frozen map stays until the next tag change. Children's maps are built from `parentTags.freeze`, same race. (c) Tag changes do not call `invalidateSnapshot`, so `_snapshotScenarioStack` (which captures `nodeInputs.freeze`, SnapshotSupport.scala:98) and `_asBasicScenarioStack` keep old tags until the next tweak change; `SnapshotScenarioStack.equals` ignores tags (:218–223). (d) No node invalidation on tag change (by design, presumably; plugin tags are scoped SI inputs; ring 3 question).

<a id="a9"></a>**A9 (M) Partially applied batch visible to tweak expansion.** `UpdateMultipleScenarios.evaluateAndApplyTweakLambdas` applies `tweaks.toSeq ++ sorted` one tracker at a time (UpdateMultipleScenarios.scala:61–65). Each `doAddTweaks` first *evaluates* `TweakExpander.expandTweaks` in that tracker's live stack (TweakContainer.scala:118–120), which already reflects the trackers applied earlier in the same batch. Plain tweaks are applied in `Map` iteration order (insertion order up to 4 keys, hash order beyond); lambda results bottom-up. So `addTweakMapImmediate(Map(P -> x := 2, C -> <tweak needing expansion that reads x>))` expands C's tweak with x = 1 or 2 depending on map size and hash order. Needs check of which tweak kinds set `hasUnresolvedOrMarkerTweaks` (Scenario.scala:67) and whether their RHS reads other tweakables at expansion time.

<a id="a12"></a>**A12 (M, needs misuse) Live stack exposed.** `final val scenarioState = scenarioStack.asScenarioState` (DependencyTracker.scala:145; `ScenarioState(this)`, ScenarioStack.scala:193) and `final val nc_scenarioStack` (:150) are public. Evaluating with them (`given(tracker.scenarioState)`) bypasses queue and cancel scopes: reads the `JHashMap` while an update mutates it (CacheIDs.scala:408–412 assumption broken), and, worse, a node computed from half-applied tweaks is inserted into the cache under the tracker's (stable, mutable) cache id; if its TTrack registration lands after the invalidation pass, nothing ever invalidates it. No caller in this repo; the UI code is not here.

**A15 (L–M) `throwOnDuplicate` is ignored.** `MutableTweakContainer.doAddTweaks` never reads `throwOnDuplicate` (TweakContainer.scala:107–130); `changesFrom` silently overrides. Callers pass it deliberately (`newChildScenario` passes `true`, DependencyTrackerChildren.scala:97; `Settings.throwOnDuplicateInstanceTweaks` default, DependencyTrackerBatchUpdater.scala:93). Duplicates *within* one call may be caught by `Scenario(tweaks)`; duplicates against existing tweaks are not. Dead setting.

**A16 (L) `ImmutableTweakContainer` asymmetry.** Adds throw; removes are silent no-ops (TweakContainer.scala:208–226).

### Foot-guns

- Sync API from a graph thread blocks a scheduler thread on a latch without helping (DependencyTrackerAction.scala:207); enough concurrent sync calls with a queued update deadlock the pool. Sync updates under a sync stack trip the scheduler's OPTIMUS-43488 guard (message at OGScheduler.java:1686–1692 names this case).
- `track`/`trackUpdate` (DependencyTrackerSyncApi.scala:30–40) and `setPluginTag` bypass the queue.
- `DependencyMultiTrackerEvaluator.safeToEvaluate` increments a counter as a side effect, inside an `Option.filter` in `getCurrentEvaluator` (DependencyTracker.scala:180–182), and must be paired with `finishEvaluating`; a missed pair makes every later update spin forever in `waitForEvaluations` (DependencyTrackerBatchUpdater.scala:449–458), which also busy-spins a graph thread with `Thread.yield`. No caller in this repo.
- `scenarioStackWithCancelScope` caches a copy whose `_parent` is frozen at copy time (DependencyTracker.scala:192–201 vs UnderlayScenarioSupport.scala:36). Correct only because every phase installs a new scope; a future change that reuses a scope across an underlay change would make evaluations see the old underlay.
- `newChildScenario`: name-uniqueness check-then-act across `childByName` and `addedChild` (DependencyTrackerChildren.scala:89–96); construction not queued; `appletName = null` for children (:93).
- Invalidation callbacks registered via `registerNodesInvalidated` can be called unbatched, from arbitrary threads, under internal locks (A4).
- `executeBatchUpdateAsync` defaults `scheduler = Scheduler.currentOrDefault` (DependencyTrackerAsyncApi.scala:91), contrary to the reasoning at DependencyTrackerAction.scala:111–115 (an aux scheduler on the calling thread captures all later updates).
- Shutdown hook per root on the parent stack's environment (DependencyTrackerRoot.scala:70–84); with `RuntimeEnvironment.minimal` (shared global) the closure chain grows with every root ever created.

### Performance

- A7(b) producer blocking; A10 starvation.
- `waitForCancelledNodesToStop` is called for every scheduler on every phase end and every batch op (`Scheduler.schedulers.foreach`, DependencyTrackerQueue.scala:418, :443), each taking that scheduler's `_lock` to snapshot all stacks. A batch with k mutating ops does ≥ k + 2 of these.
- `scenarioStackWithCancelScope` misses whenever the tracker's base cancel scope is not `NullCancellationScope`: `withCancellationScope` returns a stack with `cancelScope.union(cs)`, never `eq cs` (ScenarioStack.scala:835–838, CancellationScope.scala:274–280), so `nodeOf` allocates a stack copy per key.
- `setUnderlay` dups the cache id of every underlay level (UnderlayScenarioSupport.scala:141): all underlay nodes become unreachable in cache, and the old/new tweak union is invalidated wholesale (over-invalidation acknowledged at :56–58).
- `invalidateByPropertyMap` scans all TTrack roots of every tracker in the subtree (TweakableTracker.scala:262–284).

### Properties that hold

- **Per-queue reader/writer exclusion with a cancel-scope barrier** (DependencyTrackerQueue.scala:126–145, :412–445). The cancel scope is a cheap epoch: rather than tracking every orphan, cancel the epoch and wait only for nodes *currently on a stack* (OGScheduler.java:1640–1668). Suspended orphans are stopped by the scheduler's cancelled-scope check before they can run again. This is the property that keeps `invalidateCache` off running nodes (the R6/R8 shapes) on the normal path. Do not break: any new evaluation entry point must take its cancel scope from the queue.
- **Child scopes nest under parent scopes** (:403–406), so a parent's barrier stops descendant-queue orphans too.
- **No user code under `queueLock`**: `raiseCallback` and invalidation-batch callbacks run outside it.
- **FIFO between updates and evaluations, with evaluation batching** (:314–333): an update never overtakes earlier evaluations and is never starved by later ones on the same queue.
- **Batch-updater async callbacks inline** (DependencyTrackerBatchUpdater.scala:665–678), so the spinning update thread cannot starve them, and they are immune to the cancelled-scope skip in A3.
- **Callback lists are copy-on-write volatile lists** (CallbackSupport.scala:20–35).
- **Disposal on the root queue** means the whole tree is quiescent during dispose.
- **Tweak changes mutate one shared cache id instead of rebuilding stacks**, so cached nodes that do not depend on the change stay valid with no re-keying; correctness rests on TTracks (ring 4b) and the barrier.
